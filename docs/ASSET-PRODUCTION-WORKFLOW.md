# 素材制作・組込みワークフロー

目的：イメージ画像で終わらせず、**再利用できるゲーム部品**として分割生成・置換・検証する。「雰囲気が近いが未実装」を完成とみなさない。

## 0. 入力として固定するもの

素材に着手する前に1枚のブリーフを作る。

| 入力 | 必須の決め事 |
| --- | --- |
| 目的 | どの画面の何の状態を改善するか。恐怖の要素は人数・影・向き・時間など一つに限定 |
| 見た目 | フォトリアル／古紙／暗い室内、彩度・陰影・構図・レンズ・人物の距離 |
| ゲーム内役割 | 背景／主体／差分／UI縁／装飾／キャラ／ポートレート |
| 必要な状態 | N（平常）、R/SR/SSRなど異変段階、暗所、選択、使用済み |
| 位置条件 | アスペクト、セーフエリア、中央の主役、見切れ禁止、タップ可能な座標 |
| 出力契約 | ファイル名・ID・解像度・形式・透過・枚数・再生成可能なプロンプト |
| 検収 | 比較対象の現行スクショと、変更後の320/390/430px・横画面 |

画面モックを一枚生成するだけでは部品化にならない。**背景→対象物→異常差分→装飾/操作縁**の各要素で独立した画像、または同じ構図の差分を持つ。

## 1. 生成から公開までの工程

\`\`\`text
ブリーフ確定
  → 既存素材と画面の監査
  → 平常の構図（ベース1枚）
  → 異常の差分（同構図・同カメラ）
  → 状態表・接触位置・ID台帳
  → 最適なWebP/SVG/透過PNGへ加工
  → GitHubへ配置・HTML/CSS/JSから参照
  → デコード/外観/入力/保存テスト
  → 320×568 / 390×844 / 430×932 / 844×390 のスクショ
  → CI・PR・マージ・公開反映確認
\`\`\`

**生成完了・加工完了・組込み完了・公開確認は独立したチェック項目。**

## 2. 1場面を4状態で管理する

例：駅のホーム

- 基準：ベンチには人がいない。通常の空間として自然に成立。
- R：人数だけが1人増える。ほかの物理条件は維持。
- SR：監視記録には増えていない。写真の記録だけが増える。
- SSR：写真に人は存在するが記録者の時刻が未来になっている。

初期に観測者が発見できる異常は**1つ**。構図・人物の向き・照明を大きく変えると単なる別画像になり、差異を認識できなくなる。単独で見るだけでも成立するか／比較で分かるか、両方をレビューする。

## 3. 既存の素材置場と扱い

| 置場 | 扱い |
| --- | --- |
| \`assets/intro/\` | 最初の3通と救出。写真before/after、構内図、メモ、7点の画像マニフェストあり |
| \`assets/observation/\` | 4方式のスプライトと \`*-variants.webp\`、追加平常背景のSVG4点 |
| \`assets/incursions/cases/\` | 000〜099の100事件画像。IDと保存意味を固定 |
| \`assets/colleagues/\` | 3人の個別肖像。小画面でも輪郭で区別 |
| \`assets/ui/\` | 机・封筒・フォルダー・ボタン縁・レーダー・警告など。クリック領域はHTML |
| \`docs/INCIDENT-IMAGE-*.json\` | 異変絵の入力、マニフェスト、上書きの既存台帳。書換え前に差分を読む |

収集・接触座標が紐づく素材IDは変更せず追加する。単に背景を差し替えた場合に「新しい地点」「新しい図鑑レコード」と報告しない。

## 4. アセット台帳の1項目（推奨）

\`\`\`json
{
  "id": "observation/cctv/new-place/v1",
  "status": "draft",
  "scene": "地下通路",
  "base": "scene-base.webp",
  "variants": ["scene-r.webp", "scene-sr.webp", "scene-ssr.webp"],
  "aspect_ratio": "2:1",
  "target_coordinates": "native-image-normalized",
  "prompt_reference": "docs/prompts/scene-id.md",
  "usage": ["observation"],
  "source_revision": "unverified",
  "qa": {
    "decode": false,
    "mobile_view": false,
    "hit_targets": false,
    "save_compatibility": false
  }
}
\`\`\`

\`status\` は \`draft\`（原案）→\`generated\`→\`processed\`→\`integrated\`→\`qa_passed\`→\`released\`。未完の状態で先にチェックを付けない。ファイルやプロンプトは**新規素材に適用する推奨台帳**であり、既存の全素材がこの形式を持つとは主張しない。

## 5. 出力・画像処理

- 背景：比率を画面に合わせる。文字や押下風ボタンは素材に焼かない。
- 人物・対象：背景から切り分ける。背景と人物の輪郭を保ち、疑似透過の縁・白フチを残さない。
- 異変差分：基本画像の原点と射影を一致させる。差分が重なる位置での比較が成立するか測る。
- CSSでの光やノイズ：画像を見えなくする後処理はしない。静かな演出を端に限定。
- WebP：描画用途に応じて解像度と容量を調整。最低解像度や品質値は実測・画面サイズで選び、無根拠な統一をしない。
- SVG：テキスト命令と比較・リサイズしやすい平常背景には適するが、写実性が必要な場面の代用品とみなさない。
- スプライト：1枚から座標切出しする場合は、全状態のセル境界、比率と対応する接触位置をテストする。

## 6. 実装上の接続チェック

- マニフェスト内の画像ID・URLとゲームコード内のパスが一致するか。
- 画像の \`decode()\` とfallback。ロード途中に黒い表示だけを残さない。
- \`background-size\`、\`object-fit\`、左右スプライトの切出しとセーフエリアが一致するか。
- 画面が縮小しても画像上の異常ターゲットを直接触れるか。3×3の場所選択でも同じ処理になるか。
- 文字/CTA/閉じる操作が装飾や固定ナビに隠れないか。
- 演出軽減をONにしたとき、素材の表示自体が消えないか。
- 旧セーブの記録と画像IDは元の意味を保つか。

## 7. 実例から得たこと

- 「1枚絵を全部UIとして使う」→量産は速いが分割配置・ボタン・文字・解像度対応が難しい。最初から背景/対象/差分/前景/操作を分ける。
- 「とりあえず背景の種類を増やす」→同じ保存IDとイベント画像を使い回しているだけなら独立地点ではない。場所と記録を別々の概念として定義する。
- 「画面の見た目がよい」→実機で重なり、タッチ、文字が読めないことがある。必ず画像と操作を両方QAする。
- 「画像を制作した」→画像バイト列がリポジトリへ入っていなければ公開物ではない。**GitHubのテキスト編集APIだけではWebPなどのバイナリ配置を完了できない場合がある**。その場合は未組込みと報告し、正規のバイナリpush経路を確保する。
- 同じテイストを保つには背景・人物を一体生成するより、光源・遠近・粒状感・人物シルエットを共通のスタイルブリーフで管理する。

## 2026-10-15 SSR観測素材の再現可能な事前合成

- 原本のCC0写真4枚、写真由来透過WebPのSSR差分4枚、作者設計SVGのSSR手掛かり4枚は個別素材として**保持**し、ゲームのSSR表示時のみ派生WebP1枚へ合成する。
- 生成コマンド：`python -m pip install Pillow==12.0.0 CairoSVG==2.8.2` → `python scripts/build-ssr-composites.py`。検証のみは `python scripts/build-ssr-composites.py --check`。
- 出力：`assets/observation/ssr-composites/{cctv,photo,vision,dash}-3.webp`。1440×720の2:1画像空間は保持し、元の異変中心座標、タップ範囲、抽選/報酬/セーブは変更しない。
- `docs/qa-incursions/ssr-composite-build.json` は4つの入力ソースと出力のSHA256/寸法/サイズを記録。Smokeの `tests/ssr-composite-asset-audit.cjs` が本体バイナリと照合し、未作成・原本更新の生成漏れをCI失敗にする。
- 初回生成は専用の一時的な権限付きGitHub Actionsでバイナリをfeatureブランチへpushした。生成後は権限付き一時ワークフローを削除し、出力の来歴とスクリプトのみ通常のリポジトリに残す。
- **品質の境界**：写真と差分が重なるという機械判定と、人間が違和感に気づくか/怖いかは別。レンダラの初回失敗率・実iPhone Safari・プレイテストは #141/#75/#89 に残す。

## 8. 素材のDone条件

1. ファイルと生成意図が台帳で追える。
2. 目的の全状態がある（必要な個数を省略していない）。
3. 実際のゲームに配置し、旧画像の残存や黒画面がない。
4. 所持ID・報酬・当たり領域のテストが通る。
5. スマホ画面と低刺激設定を画像で確認。
6. PR・CI・マージ・公開版で一致が確認できた。
