# 真相ガチャ 仕様書と設計書の更新手順

ゲームのアップデートでは、コードと同じPRで現行仕様と体験設計への影響を確認する。正本を増やさず、現在の振る舞いは[現行仕様書](CURRENT-SPEC.md)、画面・演出・情報提示の判断基準は[体験設計書](EXPERIENCE-DESIGN.md)に記す。[システム構成](SYSTEM-ARCHITECTURE.md)や個別分野の詳細書は、実装契約が変わる場合に併せて更新する。

## 変更前に確認すること

1. 最新main、Open PR、Issue、CIと、変更対象に対応する仕様・設計の章を読む。過去のチャットや日付付き資料を現在の実装とみなさない。
2. 変更がプレイヤーの操作・表示、ルール・数値、保存・権限、素材・情報秘匿のどれに影響するかを決める。
3. 仕様書には「今どう動くか」、設計書には「なぜその体験にするか」を書く。予定や未承認案を実装済みと混ぜない。

## 同じPRで更新すること

| 変更 | 主な更新先 |
| --- | --- |
| ルール、経済、解放、保存、公開上の振る舞い | 現行仕様書の該当章。保存境界が変わればシステム構成も更新 |
| 画面構成、操作導線、アクセシビリティ、ホラー表現 | 体験設計書の該当章。プレイヤーに見える振る舞いは現行仕様書も確認 |
| 画像・音・生成素材の本番組込み | 両書の該当箇所と素材台帳。生成済みと公開済みを分ける |
| テスト、CI、内部リファクタのみ | 両書への影響を確認。影響がなければPR本文にそれぞれ具体的な理由を書く |

変更された内容だけを直し、日付やSHAだけの更新を仕様変更の代用にしない。古い決定の理由は履歴資料へ残し、現行書の本文では採用済みの挙動を先に読めるようにする。テスト成功、本番公開、実機検証、人による体験評価は別の到達状態として記す。

## PRとCIで確認すること

- PRテンプレートの「仕様書」「設計書」を確認する。更新した場合は差分を示す。影響がない場合は、各行に `仕様書: 影響なし — 具体的な理由`、`設計書: 影響なし — 具体的な理由` と記す。
- `index.html`、`assets/`、`firebase/`、Webアプリのマニフェストまたはサービスワーカーを変更したPRでは、軽量CIが両書の更新または各書の影響なし理由を検査する。理由の妥当性はレビュアーが判断する。
- 文書のリンク・必須章は `tests/documentation-contract.cjs`、更新契約の分岐は `tests/spec-design-sync.cjs` で検査する。CIの通過だけで記述内容の正しさは認定しない。
- レビューではコード・テスト・二つの書の内容を照合する。矛盾があれば同じPRで直す。マージ後はmainとPagesの結果を確認し、未検証の実機・本番・人間評価はIssueに残す。

文書だけの変更でも、最新mainに照らして事実を確認し、変更後のリンクと構造を検査する。新しい大きな方針や未決定の世界設定は、この手順によって自動承認されたことにはならない。
