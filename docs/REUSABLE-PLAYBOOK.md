# 再利用プレイブック：小規模ゲームをAIで仕上げる型

目的：真相ガチャの制作で得た**「再現可能なプロセス」**だけを抽出し、題材や世界観の違うゲームへ転用する。個別の文字・画像・数値をコピーする手引きではない。

## 1. 最重要の再利用資産は画像ではなく「契約」

別タイトルへ持ち込む順番：

1. **体験契約**：初回3秒で何を見せ、何を感じさせたいか。
2. **ループ契約**：1回の行動→反応→発見→次の期待→休息。
3. **データ契約**：ID、保存、解放、報酬、移行、重複禁止。
4. **素材契約**：背景・人物・差分・タップ領域・台帳。
5. **画面契約**：1画面の目的、主要CTA、ナビ、解像度・操作。
6. **品質契約**：自動テスト＋実ブラウザ＋スクショ＋実機＋プレイテスト。
7. **公開契約**：PR・CI・main・本番・未確認項目。

AIは「言われた画面を作る」のではなく、まずこの7つを明文化してから小さく改善する。完成の約束は曖昧な「いい感じ」ではなく、観測可能なDone条件にする。

## 2. AIに任せる単位

| 作業の種類 | AIの得意な作業 | 必ずレビューすること |
| --- | --- | --- |
| ループ設計 | 行動・報酬・開放・状態を構造化 | なぜ繰り返したいか、単調化しないか |
| UI/UX | 一画面1目的、スマホ配置、画面切替 | 390×844画像、文字、重なり、実タッチ |
| 資料・台詞 | 多数の差分、同テーマの連続性 | 事実誤認、同じ表現の乱発、不気味さの量 |
| アート | ベース画像、状態差分、個別パーツ | モック寄せ、同一光源、統一構図、ファイル配置 |
| 実装 | モデル、保存移行、テスト追加 | 既存main・回帰、IDと抽選、権限 |
| QA | 連打・リロード・短い画面・異常系の自動化 | 人間の体験と本番環境は別確認 |
| 運用 | PR、Issue、Docs、手順を整える | 実際のCIとmain/公開版が一致しているか |

## 3. 失敗から学んだアンチパターン

| 失敗 | なぜ起きるか | 改善策 |
| --- | --- | --- |
| UIが情報で埋まる | 新機能の説明を全て常設 | 主要CTAと映像を先に置き、機能は条件付き解放 |
| 画像の品質がばらつく | 場面ごとに異なるプロンプトや比率 | 平常ベース・共通スタイル・差分のみ変更 |
| モックから離れる | コードの都合で素材や構成を変更 | モックとの前後スクショ比較をDone条件に |
| 画像を作って終わる | 生成と実装が別工程 | 素材ID→配置→decode→画面→CIまでを一作業 |
| 同じロケーションばかり | 表面のラベルを変えただけ | 本当の場所ID/記録ID/画像/巡回を別々に設計 |
| 次の機能で前の操作が壊れる | 状態と画面の依存が散っている | 入口の共通モデルと境界・セーブテスト |
| CIだけ通ったのに操作不能 | DOM検証だけ、スクショなし | 人が代表スクショを見る。実ブラウザでCTAを押す |
| テストを消して終わらせる | 納期圧力と原因追跡の省略 | 失敗を根拠に修正、回帰を残す |
| 恐怖＝赤ノイズ・フラッシュ | 感情の設計がない | 平常を成立させ、1点の異常→不一致→余韻 |
| いつまでも残タスクが曖昧 | 未実装と未確認が同じ箱 | Issue・PR・CI・公開・実機を分けた状態表 |
| 会話をまたぐと仕様がずれる | 最新mainより古い要約を信じる | docs/INDEXとmainを先に読み、履歴はあとから参照 |

## 4. 他ジャンルへの移植方法

### 釣り・冒険・育成

- 真相ガチャの「平常と異変の差分」を、魚影の小/大、食いつく直前の変化、天候・水面の違いに変える。
- 「観測→気づき→介入」は「探す→魚影を読む→投げる/巻く」に置換する。赤いノイズや都市伝説の文章は移さない。
- 「写真差分を同じ構図で作る」は背景海面、魚影、キャラ、竿、エフェクトの別パーツ管理へ転用する。
- 実操作は中央の主要体験に集約。入力方向やゲージなどは独立した変数・検証対象にする。

### アクション・複数のミニゲーム

- 1作品1コアループ。ランクや解放はタイトルごとの成長体験に従う。
- ボスとザコで見せ方の重要度を分ける。モックの世界観を守りながら画面単位で視認性を上げる。
- 共通化するのは画面内のセーフエリア、タップ・スワイプQA、素材台帳、保存テスト、PRフロー。
- **別タイトルのゲームメカニクスまで一律コピーしない**。

### 収集・資料系ゲーム

- 同じ素材の再訪に「新しい意味」を持たせる。初回だけでなく、差分、証言、比較、再鑑定。
- 未取得情報は隠すよりDOMに生成しない。コレクションの最大数を必要以上に示さない。
- レアリティ、対象数、必要回数と恐怖/発見の頻度は、**別のパラメータ**として管理する。

次に解放する情報：

## 6. エージェント向けプロンプト例

\`\`\`text
最新main・open PR・CI・Issueを最初に確認。
既存の体験・保存ID・数値・素材に影響する箇所を洗い出す。
1画面1目的・スマホ390×844を基準にし、既存モックを上回る改善ではなく
まずモックの重要な構成と主役の視認性を守る。
画像は背景／対象／異変差分／装飾に分割し、再利用できる単位と台帳を持つ。
新規機能は取得→閲覧→操作→保存→再読込→報酬の一連のテストを用意。
テスト失敗を削除・スキップで隠さず修正する。
完了時はスクショ・CI・PR・main・公開の確認範囲と未確認を明記。
目的/成果物/制約/Done条件/自走範囲を整理し、途中確認は必要な権限時のみ。
\`\`\`

## 7. チームの継続学習サイクル

\`\`\`text
ユーザーフィードバック
   ↓
違和感／離脱／スクショ／操作ログを分類
   ↓
仮説（体験・見た目・機能・性能）
   ↓
1つの測れる変更
   ↓
モデルテスト・画面QA・プレイテスト
   ↓
結果を記録（改善した・しない・未測定）
   ↓
ルール・テンプレート・テストへ昇格
\`\`\`

1回限りの改善を「スキル」にせず、**違うタイトルでも同じ失敗を防げるテスト・チェック・プロンプト**に変換するのが最終目標。

## 8. 再利用してよいもの／避けるもの

- 再利用する：仕様ブリーフ、データ移行と二重支給禁止、台帳、レイヤー生成、画面比較、レビュー様式、QAゲート。
- 原則再利用しない：世界観固有のセリフ、恐怖表現の色、抽選数値、機密ランク名、他タイトル固有の操作体系。
- 参照だけする：別タイトルの成功シーンとプレイヤー行動。実測されていない演出を「成功確定」としない。
