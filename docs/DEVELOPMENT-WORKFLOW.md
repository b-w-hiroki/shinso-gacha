# AI・人間混成 開発ワークフロー

目的：細かな途中確認を増やさず、**最新mainを壊さず、ゲーム体験と公開品質を継続改善する**。この手順は真相ガチャを基準とするが、他の小規模ゲームにも使える。

## GitHub Issue・判断・Projectsの運用（Pilot）

現在は [GITHUB-WORKFLOW-PILOT.md](GITHUB-WORKFLOW-PILOT.md) を適用する。共通仕様はPrivateの `studio-playbook/docs/GITHUB-OPERATING-MODEL.md` が正本であり、この作品では既存の `@task-brief` / CI / PR / main / Pagesフローを維持したまま **DecisionとTaskをIssueへ記録**する。

1. チャットで企画・判断・作業が確定したら、同じ問題のIssueを検索し、無ければ実装Task/Decision/Bugに分けてIssueを作る。
2. 人が決めるDecisionは採用/却下と理由が記録されるまで他Taskをブロックしない範囲で分離。未公開内容やSecretを公開Issueへ書かない。
3. Epicはリンクとチェックリストの索引。個別タスクは独立Issue、結果はPR・CI URLへ結び付ける。完了以外ではPR説明に `Refs #...` を使い、`Fixes` で誤自動Closeしない。
4. Issueの優先度はP0/P1/P2、実行許可は `autopilot:ready` 等の既存条件を維持。Projectsが読めないときはIssueを実行上の正本とする。
5. パイロットは共通Playbookで合格条件を判定し、承認後の正式採用はポリシー状態を変更する。既存Issue/判断は削除しない。

## 1. 作業ブリーフ（@task-brief）

どの仕事も開始時にこれを1枚へ変換する。

\`\`\`md
# タスク名
## 目的
プレイヤーに起こしたい変化を1〜2文で
## 成果物
修正対象、画像、コード、文書、テスト、PR
## 制約
保存互換、世界観、参照モック、低刺激、スマホ、予算、非対象
## Done条件
実装／画面の比較／各種テスト／PR・merge／公開確認
## 自走可能範囲
探索、実装、素材生成、テスト、調整、差分レビュー
## 外部に必要な権限
本番Firebase、本番アカウント、GitHub画像バイナリpush、実機など
\`\`\`

「画像を増やす」は目的ではなく手段。「観測先を増やして同じ景色の繰り返しを防ぐ。ただし異変を見つけられる構図は保つ」が目的。実装に必要な変更をまとめたうえで作業する。

## 2. 一連の実行フロー

\`\`\`text
01 現状確認
  ↓
02 差分・問題の棚卸し（P0/P1/P2）
  ↓
03 完了条件と変更境界の確定
  ↓
04 必要素材・データモデル・画面案の準備
  ↓
05 実装（小さな意味のある差分）
  ↓
06 自動テスト・ブラウザQA・スクショ比較
  ↓
07 不具合の切り分けと再検証
  ↓
08 ドキュメント・Issue・PRへ証跡
  ↓
09 CI全通過 → merge → ブランチ掃除
  ↓
10 main/公開版確認 → 残タスク更新
\`\`\`

**作業前に必ず main・open PR・CI・Issue・既存設計書を確認。** 前のチャットでの記憶や古い引き継ぎをmainへ上書きしない。

製品アップデートでは、[現行仕様書と体験設計書の更新手順](SPEC-DESIGN-WORKFLOW.md)を同じPRへ適用する。仕様は実際の振る舞い、設計は判断基準を記し、影響しない書はPR本文に理由を残す。文書の更新だけでテスト・公開・実機検証が済んだとは扱わない。

## 3. 役割分担（AIの役割は一つに固定しない）

| 役割 | 成果 |
| --- | --- |
| ディレクター/PM | 目的・体験・優先順位・Done条件 |
| 企画/システム設計 | ループ、状態、保存、確率、イベント、解放、リスク |
| アート/アセット | ベース・差分・文字なし素材・台帳・実組込み |
| 実装 | 単一の既存モデル経路、UI、保存移行 |
| QA/レビュアー | 独立視点で「動くか」「見た目は正しいか」「遊びとして成立するか」 |
| リリース担当 | 権限・CI・マージ・GitHub Pages/本番Firebaseの区別 |

一つのAIセッションで兼務しても、**制作者が「完成した」と判断しただけでQA済みにはならない**。レビュー段階で仕様の不変条件と証拠を分ける。

## 4. 調査フェーズ：先に観測すること

1. 既に入っている実装を探す（同じ機能の二重作成を禁止）。
2. 最新コードからデータ型、保存キー、画面、抽選・報酬の所有者を見つける。
3. 対応する既存テストとスクショを探す。
4. 実際に解消したいユーザー問題を言語化する（例：「写真が増えたのに人物が読めない」）。
5. ブロッカーと変更できる範囲を切る。画像バイナリ、本番権限、実機が必要なら早期に区別する。
6. 関係ないCSS上書き・画面全面変更・既存IDの番号振り直しをしない。

## 5. 小さく進める設計

- 1PRは原則**1つのプレイヤー価値**。例：「3人の証言を照合できる」→モデル、UI、保存、テスト、資料は同PR。
- モック寄せ・ゲームロジック・大規模リファクタを無関係に同時実施しない。競合が増え、問題の原因を判別しづらい。
- レイヤー素材を先に作ってから実装に進むなら、その状態をIssueに保存。「素材生成済み」のあと必ず配置・QAをタスクとして残す。
- 古いコードを置き換える際は**mainの最新差分を確認**し、コンフリクトを \`ours\` / \`theirs\` 一括採用で解決しない。
- 重大変更は先に移行テストを書く。保存の読取り→正規化→既存報酬不変を確認。

## 6. 実装から検証の基本サイクル

\`\`\`text
変更した1機能のモデルテスト
  → 関連UIテスト
  → 一般人と調査員、既存ユーザーの回帰
  → 320/390/430px縦、短い横画面、PC
  → 日本語改行、下部CTA、重なり、閉じる操作
  → quiet / prefers-reduced-motion / キーボード・場所選択
  → 保存・再読込・連打・多重報酬・日付境界
  → CI / PR / main
\`\`\`

- 失敗した検証を削除・スキップして「成功」にしない。根本原因を直し、必要ならテスト側が古い操作を参照しているか精査する。
- 真相ガチャは「描画できた」だけでは不十分。差分の手がかりが読めたか、ボタンが届くか、画像上の操作が正確か、必ず画像も確認する。
- CIにはNode/Chromium/WebKit/Firestore emulatorがある。安全なmock検証が成功しても本番Firebaseを保証しない。

## 7. GitHub・CI・PR運用

1. ブランチを最新mainから作る。
2. モデル・画面・素材・テスト・仕様を変更。HTMLのインラインスクリプト変更時は \`node scripts/update-csp.cjs\` を実行し、CIで \`--check\` を通す。
3. PRには「目的／変更箇所／保存互換／画面差分／確認済み・未確認／関連Issue」と、仕様書・設計書の更新または個別の影響なし理由を書く。製品ファイルの差分は `spec-design-sync` CIが記入漏れを検査する。
4. CIの完了を確認する。自動テスト中に別のPRを混ぜない。
5. Browser artifact の代表スクショを開き、タップ/文字/画像の品質を確認する。
6. PRのhead SHAが想定と一致する状態でマージする。
7. mainに入ったSHAを確認し、使い捨てブランチの自動削除を確認する。
8. 公開画面の反映確認。未確認なら公開済みと断言しない。

GitHubコネクタではテキストファイル変更は可能だが、環境によって**画像バイナリのpush・ローカル実機Safari・Firebase本番操作には別の正規手段が必要**。できなかった作業を架空の完了として埋めない。

## 8. 進捗の状態表現

| 状態 | 判断材料 |
| --- | --- |
| 未着手 | Issue・仕様のみ |
| 設計済み | データ・画面・ID・入力・素材出力の契約が決まった |
| 素材生成済み | 画像は存在するが、ゲームへの配置と公開は未確認 |
| 実装済み | ブランチ/コードに実装がある |
| テスト済み | 該当モデル/UI・保存・レイアウトテストが成功 |
| マージ済み | mainに取り込んだSHAを確認 |
| 公開確認済み | Pages等の配信実体がmainの内容と一致 |
| 実機検証済み | 指定OS/端末で操作・見た目・保存の実測を記録 |
| 本番運用確認済み | 認証・ルール・同期など本番サービスで検証 |

「進めている」「終わった」だけでなく、**最後に到達した状態**と残りを伝える。

## 10. 長期開発で改善を続ける方法

- 各PRの終了時に「失敗と対処」を短く記録し、同じ問題を再現テストに変える。
- 毎回タスクを1件だけ増やすのでなく、同系統の作業を「素材の質／ゲームとしての価値／開発基盤」の三層に分類する。
- 現行仕様に設計変更を反映し、過去の変更の理由は設計履歴に残す。ユーザーに同じ前提を何度も尋ねさせない。
- 週次でP0とP1の未完を確認。ゲームとして怖い・楽しいかは少数の人間のプレイテストで評価する。
